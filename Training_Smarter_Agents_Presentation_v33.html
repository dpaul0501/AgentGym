We will use TravelSage as the example agent system

request

“Plan a Geneva → Lisbon trip under €500. Prefer Star Alliance. Avoid overnight transit unless it saves more than €120. Verify policy before final booking.”

A full TravelSage run can trigger flights, hotels, local transport, budget checks, policy checks, memory, and itinerary planning.

example system

TravelSage is a compact multi-agent workflow where the moving parts are easy to recognize: tools, memory, KB/RAG, structured constraints, specialist agents, and an orchestrator.

The same architecture shape appears in support, finance, research, claims, operations, and coding agents.

Use case: simple enough to follow; rich enough to expose the agent-improvement problem.

An agent is a loop: observe, reason, act, repeat

A single TravelSage failure can come from several places

captured execution
t1 Policy Agent retrieves generic Schengen note
   → misses Spain-specific transit rule

t2 Flight Agent searches GVA → LIS with budget=500
   → ignores later budget update to 720

t3 Flight Agent repeats almost the same search
   → duplicate tool call, no new evidence

t4 Orchestrator finalizes without policy gate
   → unsafe completion path
improvement scope

An engineer could try several things:

  • optimize prompts, retrieval, memory, or tools
  • replace a chain with a multi-agent graph
  • add verification, routing, or recovery logic
  • fine-tune or adapt a travel-domain model

Today these choices often feel ad hoc. The talk turns them into a common training-and-optimization framework.

Under the hood: an agentic system around ReAct steps

key idea

Every agent execution is made of repeated ReAct steps.

Context → Action → Observation

For an LLM, context is mostly tokens from the prompt and previous generation. For an agent, context is assembled from the user request, memory, retrieved evidence, tool results, active skills, permissions, and orchestrator state.

What an agent is made of

The trajectory is controlled by three broad levers

LeverWhat it controlsWhat it looks like in TravelSage
φ · Contextwhat information reaches each ReAct stepmemory slots, retrieved policy passages, tool schemas, skill instructions, previous observations
ρ · Harnesshow execution is routed, constrained, verified, retried, and stoppedmulti-agent graph, policy gate, duplicate-call guard, escalation rule, verifier placement
θ · Modelprobability of choosing an action given the current contexttool choice, reasoning step, final answer, structured action arguments
When the agent fails, the question is not “which tool should I use?” It is: which lever changed the trajectory?

Context means more in agents than in single LLM calls

LLM call

Context → output

context:
  system prompt
  user message
  examples
  previous tokens

output:
  next tokens / response

The model learns to produce the next response under a token context.

Agent ReAct step

Context → action

context:
  user request + memory
  retrieved KB / KG evidence
  tool outputs + tool schemas
  active skills + permissions
  orchestrator state

action:
  tool call, route, verify,
  ask user, stop, answer

The action is still conditioned on context, but the context is assembled by the agent system.

One execution is a trajectory, and the trajectory gets scored

Trajectory τ

(Context₁ → Action₁ → Observation₁)
(Context₂ → Action₂ → Observation₂)
(Context₃ → Action₃ → Observation₃)
...
Final answer / booking
Evaluator score: R(τ)
sequence view
P(trajectory | θ, φ, ρ) ≈ ∏ Pθ(Actionᵢ | Contextᵢ(φ, ρ))

The agent’s completed run is a sequence of action choices. The final reward scores the whole execution: success, compliance, preference match, cost, latency, and risk.

Improve agent = change θ, φ, or ρ to increase R(trajectory)

This maps agent improvement back to standard training

SystemInputOutputGround truth or signal
Traditional MLfeaturespredictionlabel, loss, metric
LLM trainingcontext tokensnext tokens / responsetarget text, preference, reward
Agent trainingsequence of ReAct-step contextsactions, observations, final answerstep labels, trajectory preference, final reward
SFT-like signal

When the correct next action is known: “in this context, call retrieve_policy before booking.”

RL / preference signal

When only the outcome or direction is known: “this trajectory is safer, cheaper, or more compliant than that one.”

Evaluation + benchmark define the Agent Improvement Objective

PieceWhat it meansTravelSage exampleArtifact
Metricone measurable propertycompletion, policy compliance, preference match, cost, latencydetector output
Evaluatorscoring procedure for one trajectoryrule checker, DB verifier, retrieval judge, cost calculatorevaluation code
Benchmarkfixed case distributiontravelsage_benchmark_v3.jsonlversioned dataset
Objectiveweighted score for a completed runR = success + compliance + quality − cost − latencyreward config
Agent improvement objective: choose a better θ, φ, or ρ so the same benchmark produces higher R(trajectory).

The benchmark is the frozen contract. Training data can come from traces, labels, preferences, or rollouts; the benchmark decides whether the new agent version really improved.

Example: turn the evaluation into a weighted reward

reward config
R(trajectory) =
  w1 · task_success
+ w2 · policy_compliance
+ w3 · preference_match
+ w4 · answer_quality
- w5 · tool_cost
- w6 · latency
- w7 · risk
TravelSage example
MetricWeightScore
task success0.301.00
policy compliance0.251.00
preference match0.200.75
answer quality0.150.80
cost / latency / risk penalties0.100.40
Here, R = 0.78. The exact weights are product choices; the important part is that every agent version is compared against the same reward definition.

A concrete agent version is just θ + φ + ρ

agent_version: travelsage-v17

model: theta-v4
context: phi-v11
harness: rho-v7

evaluation:
  benchmark: travelsage_benchmark_v3
  reward: travelsage_reward_v4
  trajectory_reward: 0.84
optimization loop
  • Run one agent version on the fixed benchmark.
  • Capture full trajectories and local diagnostics.
  • Change only one surface when possible.
  • Keep the new version only if reward and regressions improve.

This makes prompt tuning, harness edits, and LoRA training comparable engineering moves.

A harness config defines the runtime controller

harness_config: rho-v7
orchestrator:
  entry_agent: trip_planner
  max_steps: 12
  specialists: [flight, hotel, policy, budget]

routing:
  policy_check_required_before: [reserve_trip, finalize_booking]
  budget_agent_trigger_eur: 500

retries:
  search_trip: {max_attempts: 2, backoff_sec: [1, 3]}
  reserve_trip: {max_attempts: 1, on_failure: escalate}

  signature_fields: [tool, origin, destination, dates, budget]

  require: [budget_check, policy_check, user_confirmation]
  block_finalization_on_failure: true

  • router / escalation classifier from expert actions
  • bandit for model/tool/verifier selection
  • offline RL or search for multi-step controller behavior

why this is not model fine-tuning yet

The model may have emitted a duplicate tool intent, but the harness can still block or redirect it. The improvement target is the controller decision, not necessarily the LLM weights.

  • label: expected controller action
  • reward: success − cost − unsafe action
  • verifier: legal transition and idempotency check

interpretation

All variants are attempts to improve the same trajectory reward. The difference is which model parameters move and which supervision signal is trusted.

Agent fine-tuning data must include the state that caused the action

ObjectiveTraining recordGround truth / verifier
SFT{supercontext, target_action: retrieve_policy, target_args: {country: Spain}}expert action or verified successful trajectory
DPO{supercontext, chosen: “check policy first”, rejected: “reserve now”}preference label with reason and provenance
GRPO / RL{request, rollout_1..8, reward_vector}deterministic task, policy, cost and safety evaluators
Continued pretraining{authoritative_text}source quality, temporal validity, de-duplication
do not train on the wrong root cause

If the model failed because the policy document was absent or the harness skipped a verifier, first fix φ or ρ. Fine-tuning on corrupted traces teaches the model to compensate for bad system design.

SFT, DPO, or GRPO? Start from the supervision you can trust

SFT

Clear desired behavior

Data: expert response or trajectory.

Learns: imitation.

Risk: copies expert noise and one canonical path.

DPO

Reliable comparisons

Data: same state, chosen and rejected outputs.

Learns: judgment preference.

Risk: style bias, preference collapse.

GRPO / RLHF

Verifiable outcomes

Data: sampled trajectories + reward.

Learns: strategy discovery.

Risk: reward hacking and unsafe exploration.

Before all three

Use continued pretraining only when broad domain representations are missing. It does not by itself teach reliable agent actions or tool-use policy.

Appendix: why the trajectory is parameterized by θ, φ, and ρ

one ReAct step
Contextᵢ = assemble(user, memory, evidence, tools, history; φ, ρ)
Actionᵢ ~ Pθ(Action | Contextᵢ)

θ controls the model’s action distribution. φ controls what information enters the context. ρ controls routing, permissions, gates, retries, and stop conditions.

trajectory view
P(τ | θ, φ, ρ) ≈ ∏ᵢ Pθ(Actionᵢ | Contextᵢ(φ, ρ))
Objective: choose θ, φ, ρ to increase R(τ)

This is the bridge to standard training: define inputs, actions, labels or rewards, update the parameter surface, and re-run the benchmark.

The slide version is intentionally approximate: observations and environment transitions also matter, but the useful engineering question is which surface — θ, φ, or ρ — changed the trajectory.
